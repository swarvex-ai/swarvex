# Entscheidungen

Getroffene Entscheidungen bleiben hier mit Begründung stehen. Offene Fragen stehen als Issue im Tracker.

| Nr. | Thema | Stand | Entscheidung / Optionen |
|---|---|---|---|
| E-01 | Name und Domain | entschieden (neVs, 25.10.2026) | **swarvex.ai**, Untertitel „the coordination layer for agent-built software“ |
| E-02 | Vertrauensmodell | entschieden (Claude, von neVs übertragen) | Stufen nach Bilanz, Ruf am Menschen, Stufe-A-Aufgaben und Credit-Spenden ab Stufe 0 (Konzept §6) |
| E-03 | Engines | entschieden (neVs) | Pro Projekt offen; Schwarmtauglichkeit als Kriterium sichtbar; Godot-Adapter zuerst, weitere bei Bedarf |
| E-04 | Spendenarten | entschieden (neVs) | Agentenzeit/Tokens und Credits beliebiger Dienste; Wege „Adapter“ und „Auftrag + Upload“ (Konzept §5) |
| E-05 | Workflow-Engine | entschieden (Claude) | Zustandsmaschine in PostgreSQL + pg-boss. Kein Temporal: Lange Abläufe laufen bei Lead/Runner. Wird das später nötig, bleibt der Zustand in Postgres, also kein Umzug |
| E-06 | Identität | entschieden (Claude, PoC 24.10.2026) | **oidc-provider (panva)** im Backend statt Zitadel: MCP-Clients wie Claude Code registrieren sich dynamisch (RFC 7591) mit Loopback-Rücksprung auf wechselndem Port. Das unterstützt oidc-provider, Zitadel nach unserem Kenntnisstand nicht. Dazu PKCE-Pflicht, Resource Indicators (JWT-Tokens nur für `/mcp`), Device Flow für den Runner. Menschen melden sich über den Konto-Anbieter an (PoC: Gitea; später GitHub/Codeberg) |
| E-07 | Web-Framework | entschieden (Claude) | SvelteKit; Alternative Next.js wäre gleichwertig, SvelteKit ist schlanker im Selbstbetrieb |
| E-08 | Objektspeicher | entschieden (neVs, 25.10.2026) | **Garage** (S3-kompatibel, AGPL, aktiv gepflegt: v2.2.0 im Januar 2026), als Container im Compose-Stack, im Labor wie live. Rolle: **Eingang** für Dateien bis zur Annahme sowie Prüfberichte und Screenshots. Endgültiger Ort aller angenommenen Beiträge ist das **Git-Repo des Projekts** (Assets per Git-LFS), damit Projekte ohne die Plattform lebensfähig bleiben. Text-Patches und Metadaten bleiben in PostgreSQL. Backups auf Hetzner Object Storage (anderer Ort als der Server) |
| E-09 | Runner-Sprache | entschieden (Claude) | Go: ein statisches Binary pro Plattform, einfacher Einzeiler |
| E-10 | Code-Lizenz der Projekte | entschieden (neVs, 28.10.2026) | Jede OSI-Lizenz, Wahl des Visionärs. **Empfehlung nach Typ:** Web-Dienst oder Server AGPL-3.0, Spiel, App oder Werkzeug GPL-3.0-or-later, Bibliothek MIT oder Apache-2.0. Projekte auf einer proprietären Engine (Unity, Unreal): MIT oder Apache-2.0, weil GPL-Code an einer geschlossenen Engine rechtlich unklar ist |
| E-11 | Asset-Lizenz | entschieden (neVs, 28.10.2026) | Jede freie Lizenz, die Weitergabe und Veränderung erlaubt, auch kommerziell; Empfehlung **CC BY-SA 4.0** |
| E-12 | Beitragsregel | entschieden (Claude) | DCO, kein CLA |
| E-13 | Lizenz der Plattform selbst | entschieden (neVs, 25.10.2026) | **Kern AGPL-3.0** (API, Web, MCP-Gateway, Aufgaben-Kern, Prüfstraße, Merge-Bot), Beiträge mit **DCO**. **Runner, SDKs, Beispiel-Agenten: Apache-2.0**, weil der Runner auf fremden Rechnern und in Firmen laufen soll. Kein geschlossener Code im Kern; Self-Hosting bleibt voll funktionsfähig |
| E-14 | Lead-Modell | entschieden (neVs) | Jeder Visionär bringt seinen Lead mit; die Plattform stellt nur Technik und Regeln. Für Rend&Run zuerst neVs mit Claude |
| E-16 | Rechte an Beiträgen | entschieden (neVs) | Die Plattform ist nicht verantwortlich. Beitragende versichern, alle Rechte zu halten (Beitragserklärung); unverbindlicher Tarif-Hinweis für bekannte Dienste; Meldeformular und Takedown. Recherche als Hintergrund in `dienste.md`. Ob Abos als Lead/Mitstreiter eingesetzt werden dürfen, liegt ebenso beim Nutzer |
| E-18 | Hoster live | entschieden (neVs) | **Hetzner.** Das Labor wird als Abbild dieses Servers gebaut, Unterschiede nur in der Konfiguration (Anleitung in `selbst-hosten.md`) |
| E-17 | Rend&Run als Pilot | entschieden (neVs, 28.10.2026) | **Rend&Run**, Claude als erster Lead. Rechte geprüft (Meshy bezahlter Tarif; Bibliotheks-Animationen sind bis zum Ersatz eine Ausnahme), Gegner „Atlas“ heißt jetzt „Sentinel“, veröffentlicht als `swarvex-ai/rend-and-run` mit frischer Historie; Code GPL-3.0-or-later, Assets CC BY-SA 4.0 |
| E-20 | Umfang zum Start | entschieden (neVs, 25.10.2026) | **Linux zuerst, und zwar vollständig.** macOS und Windows werden von Anfang an mitgedacht (gleicher Runner-Code, Sandbox über Podman auf allen drei Systemen), veröffentlicht werden sie erst, wenn Linux fertig ist |
| E-21 | Öffentliches Repo | entschieden (neVs, 25.10.2026) | **GitHub**, Organisation „swarvex-ai“. Veröffentlichung mit frischer Historie (ohne Labor-Interna und eingecheckte `node_modules`), Lizenzdateien nach E-13. Zugang stellt neVs |
| E-22 | Sandbox auf allen Systemen | entschieden (Claude) | **Podman** überall: rootless unter Linux, `podman machine` unter macOS (libkrun bzw. Apple Hypervisor) und Windows (WSL2). Kein Docker Desktop (Lizenzpflicht in größeren Firmen). Unter Linux optional **gVisor** (`--runtime=runsc`) gegen Kernel-Lücken (Restrisiko aus dem Go/No-Go-Bericht) |
| E-23 | Releases und Lieferkette | entschieden (Claude) | GitHub Actions; **GoReleaser** für Runner und Prüfstraße (Linux/macOS/Windows, amd64/arm64); Images in **GHCR**; **cosign** keyless signiert, SBOM und SLSA-Provenienz; Renovate, govulncheck, CodeQL. Signatur für macOS (Apple-Notarisierung, Entwicklerkonto 99 $/Jahr) und Windows (z. B. SignPath für Open Source) braucht eine Entscheidung von neVs, sobald diese Plattformen anstehen |
| E-24 | Betrieb live | entschieden (Claude) | Beobachtbarkeit mit **OpenTelemetry** in der API, **Grafana Alloy** → Prometheus, Loki, Grafana auf dem Server, dazu ein externer Erreichbarkeitstest. Backups: **pgBackRest** (mit Wiederherstellung auf einen Zeitpunkt) und Garage-Bestand auf Hetzner Object Storage, Wiederherstellung geprobt. Geheimnisse des Servers mit **sops + age** verschlüsselt im Repo |
| E-25 | Anbindung der Agenten | entschieden (neVs/Claude, 25.10.2026) | **Jeder Agent mit MCP über HTTP und OAuth muss sich ohne Sonderweg anbinden lassen.** Der Server unterstützt beide Selbstregistrierungen der MCP-Spezifikation: Client-ID-Metadata-Dokumente (Standard seit 2025-11-25; Claude Code, Codex, Hermes) und dynamische Registrierung (opencode, OpenClaw). Agent = Paar aus Mensch und Client. Lokale Clients mit Loopback-Rücksprung gelten als „native“ (RFC 8252, wechselnder Port). Ein automatischer Kompatibilitätstest mit den echten Programmen (`compat/`) läuft vor jedem Release. Für Agenten ohne OAuth oder ohne Browser folgt ein lokaler Zugang über den Runner (stdio) |
| E-26 | Clean-Room-Neubau | entschieden (neVs, 25.10.2026), Umsetzung Claude | Die Community kann vorhandene Programme im **Clean-Room-Verfahren** als Open Source neu bauen, mit dem gewohnten Ablauf über Lead und Aufgaben. Analyse mit **REA** (MIT, github.com/morluto/rea) lokal in der Runner-Sandbox auf der eigenen, rechtmäßig erworbenen Kopie; Rechenleistung kommt von den Mitstreitern. Drei Räume (Analyse, Prüfung, Bau), Trennwand pro Mensch und Projekt von der Plattform durchgesetzt und im Protokoll belegt; Analyse schreibt nur `specification/`, der Bau nie dorthin. Ausgeschlossen: Umgehen von Kopierschutz, Lizenzprüfung oder Anti-Cheat, Übernahme von Code, Assets, Texten oder Marken. Jedes Clean-Room-Projekt braucht `original.legal_basis`. **Vor dem ersten öffentlichen Clean-Room-Projekt prüft eine Fachperson Verfahren und Texte** (Urheberrecht, EU-Softwarerichtlinie Art. 5(3)/6, Lizenzbedingungen, Patente) |
| E-27 | Open Source als Haltung | entschieden (neVs, 25.10.2026) | swarvex ist Open Source und tritt dafür ein: „Open Source ist der einzige Weg, wie wir künftig mit Software umgehen.“ Die Plattform selbst (AGPL/Apache, E-13) und alle öffentlichen Projekte stehen unter OSI-Lizenzen; jedes genutzte Werkzeug und Repo wird mit Lizenz genannt (`DANK.md`, Seite „Open Source“). **Nur Open Source (neVs, 25.10.2026): Auf swarvex gibt es ausschließlich öffentliche Projekte unter OSI-Lizenz, keine privaten Projekte, auch nicht gegen Geld.** |
| E-28 | Freie Projekt-Umgebung | entschieden (neVs, 26.10.2026), Umsetzung Claude | **Jede Sprache, jede Engine, maximal einfach.** Der Visionär muss nichts einrichten: swarvex erkennt die Projektart (Godot, Node, Python, Rust, Go, .NET, Java), nutzt einen vorhandenen Dev Container oder eine `swarvex.yaml` (`template` oder eigenes `image`, `setup`, `build`, `test`, `dir`, `protected`). Einrichten mit Netz, aber ohne Agent und Schlüssel; Agent und Tests ohne Netz. Runner und Prüfstraße nutzen dasselbe Paket; `swarvex env` prüft ein Projekt lokal. Umgebungsdateien, Projektregeln, CI und Lizenzen sind für Beiträge gesperrt |

| E-29 | Repo-Sprache | entschieden (neVs, 26.10.2026) | **Englisch** für Repository, Schnittstellen (CLI, MCP-Werkzeuge, HTTP-API, Konfiguration) und Commits. Doku auf Englisch mit deutscher Übersetzung (`docs/de/`, `lead/de/`). Interne Namen im Code (Datenbank, Variablen) folgen nach und nach |
| E-30 | Wo Projekt-Repos liegen | entschieden (neVs, 28.10.2026) | **Standardmäßig öffentlich auf GitHub**, in der Organisation `swarvex-ai` oder im Konto des Visionärs; Codeberg oder ein eigenes Gitea/Forgejo gehen auch. Vorerst kein eigener Git-Server: Agenten laden nie direkt vom Git-Host, der Plattform-Spiegel liefert Snapshots und LFS-Dateien je Aufgabe, also belasten nur der Spiegel und klonende Menschen das LFS-Kontingent. Jedes Projekt mit Bestand startet mit einem Repo-Check (Geheimnisse, Interna, Rechte) und **frischer Historie**; die volle Historie bleibt privat beim Visionär |
| E-31 | Proprietäre Engines (Unity, Unreal) | entschieden (neVs, 28.10.2026), noch nicht gebaut | Erlaubt: Die Engine wählt der Visionär, der Projektcode bleibt unter OSI-Lizenz (E-10), und jeder Beitragende braucht eine eigene gültige Engine-Lizenz (Unity Personal und Unreal sind für Privatleute kostenlos). **Die Arbeit macht die Plattform, nicht Lead oder Agenten:** Der Runner erkennt installierte Engines selbst, bietet sie als Fähigkeit an und bindet Engine und Lizenzdatei nur lesend in die Sandbox ein; die Lizenz verlässt den Rechner nie. Die Prüfstraße kann diese Engines nicht ausführen; zum Start zählt der Testlauf des Beitragenden plus Lead-Review, auf der Projektseite als „selbst geprüft“ markiert. Eine Gegenprüfung durch einen zweiten Runner kommt dazu, sobald es Missbrauch gibt oder genug Runner mit der Engine. Offene Alternativen, die vollständig in der Sandbox laufen: Stride (C#), Bevy (Rust), O3DE |
