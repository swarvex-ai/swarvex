| E-23 | Releases and supply chain | decided (Claude) | GitHub Actions; **GoReleaser** for runner and test pipeline (Linux/macOS/Windows, amd64/arm64); images in **GHCR**; **cosign** keyless signing, SBOM and SLSA provenance; Renovate, govulncheck, CodeQL. | E-24 | Operations | decided (Claude) | Observability with **OpenTelemetry** in the API, **Grafana Alloy** → Prometheus, Loki, Grafana on the server, plus an external availability check. Backups: nightly **restic** (PostgreSQL dump plus server files, encrypted) offsite, restore rehearsed with `infra/restore-test.sh`. Changed on 30 Oct 2026 from pgBackRest: one tool for database and files and native SFTP targets; point-in-time recovery is not needed at this size. Server secrets encrypted in the repository with **sops + age** |
| E-25 | Connecting agents | decided (neVs/Claude, 25 Oct 2026) | **Every agent with MCP over HTTP and OAuth must connect without special handling.** The server supports both self-registrations of the MCP specification: client ID metadata documents (standard since 2025-11-25; Claude Code, Codex, Hermes) and dynamic registration (opencode, OpenClaw). Agent = pair of person and client. Local clients with a loopback redirect count as "native" (RFC 8252, changing port). An automatic compatibility test with the real programs (`compat/`) runs before every release. For agents without OAuth or without a browser, local access through the runner (stdio) will follow |
| E-26 | Clean-room rebuilds | decided (neVs, 25 Oct 2026), implemented by Claude | The community can rebuild existing programs as open source using the **clean-room procedure**, with the usual flow through the lead and tasks. Analysis with **REA** (MIT, github.com/morluto/rea) locally in the runner sandbox on one's own lawfully acquired copy; the computing power comes from contributors. Three rooms (analysis, review, build), a wall per person and project enforced by the platform and recorded in the log; analysis only writes `specification/`, build never does. Excluded: circumventing copy protection, license checks or anti-cheat, taking over code, assets, texts or trademarks. Every clean-room project needs `original.legal_basis`. **Before the first public clean-room project, an expert reviews procedure and texts** (copyright, EU Software Directive Art. 5(3)/6, license terms, patents) |
| E-27 | Open source as a stance | decided (neVs, 25 Oct 2026) | swarvex is open source and stands up for it: "Open source is the only way we will deal with software in the future." The platform itself (AGPL/Apache, E-13) and all public projects are under OSI licenses; every tool and repository used is credited with its license (`THANKS.md`, "Open source" page). **Open source only (neVs, 25 Oct 2026): swarvex only has public projects under an OSI license, no private projects, not even for money.** |
| E-28 | Free project environment | decided (neVs, 26 Oct 2026), implemented by Claude | **Any language, any engine, as simple as possible.** The visionary does not have to set anything up: swarvex detects the project type (Godot, Node, Python, Rust, Go, .NET, Java), uses an existing dev container or a `swarvex.yaml` (`template` or own `image`, `setup`, `build`, `test`, `dir`, `protected`). Setup with network but without agent and keys; agent and tests without network. Runner and test pipeline use the same package; `swarvex env` checks a project locally. Environment files, project rules, CI and licenses are locked for contributions |
| E-29 | Repository language | decided (neVs, 26 Oct 2026) | **English** for the repository, interfaces (CLI, MCP tools, HTTP API, configuration) and commits. Documentation in English with a German translation (`docs/de/`, `lead/de/`). Internal code names (database, variables) follow gradually |
| E-30 | Where project repositories live | decided (neVs, 28 Oct 2026) | **Public on GitHub by default**, under the organization `swarvex-ai` or the visionary's own account; Codeberg or an own Gitea/Forgejo also work. No own Git server for now: agents never fetch from the Git host directly, the platform mirror serves snapshots and LFS files per task, so the host's LFS quota is only used by the mirror and by people cloning. Every project with existing work starts with a repo check (secrets, internals, rights) and a **fresh history**; the full history stays private with the visionary |
| E-31 | Proprietary engines (Unity, Unreal) | decided (neVs, 28 Oct 2026), built (Claude, 28 Oct 2026); tested in the lab with a stand-in editor, not yet with a real Unity or Unreal | Allowed: the engine is the visionary's choice, the project code stays OSI-licensed (E-10), and every contributor needs their own valid engine license (Unity Personal and Unreal are free for individuals). **The platform does the work, not lead or agents:** the runner detects installed engines itself, offers them as a capability and mounts engine and license file read-only into the sandbox; the license never leaves the contributor's machine. The test pipeline cannot run these engines. Instead the submitting runner's own test run is the first check, and the runner of **another person** with the same engine re-runs the tests (cross-check: base commit + patch, no network, no model, no tokens; MCP tools `next_check`, `report_check`). Runners take open cross-checks first. If no second runner turns up within 24 hours, the own run counts alone and is marked as such. Open alternatives that run fully in the sandbox: Stride (C#), Bevy (Rust), O3DE |
| E-32 | Agents in the runner's sandbox | decided (neVs, 28 Oct 2026), built (Claude, 28 Oct 2026); lab-tested with a fake model, not yet with a real Anthropic or OpenAI account | **Contributors choose their agent, not only their model:** `swarvex work --agent opencode|claude|codex`. Only that makes the swarm universal. Isolation is the same for all: no network except the key proxy, the real key or subscription token stays in the proxy, updates and telemetry are off, versions are pinned and at least two weeks old. The proxy passes exactly the model API of the chosen agent (OpenAI Chat Completions, Anthropic Messages, OpenAI Responses) and counts usage for each. Subscriptions work too: Claude Code with the token from `claude setup-token`, Codex with the contributor's Codex sign-in (`~/.codex/auth.json`). For Codex the sandbox gets a stand-in sign-in whose access token is the task token; the proxy sets the real token and account. The runner renews the real token like Codex does and writes it back. Own skills only with `--skills`, as a read-only copy; project skills (`.agents/skills/`) reach every agent. Agent images are built on first use. More agents: one entry in `runner/agenten.go` plus a build stage, as long as they speak one of the three APIs |
| E-33 | Runner updates | decided (neVs, 4 Nov 2026), built (Claude) | `swarvex update` runs the platform's signed installer without the setup questions; settings stay. **Automatic updates** are offered in the setup (suggestion: yes): once a day, only between tasks, then the service reloads itself. Updates only install while the platform signs with the key the runner was installed with (`release.pub`, trust on first use); a key change needs the one-liner again. Alongside: `swarvex help`, `doctor`, `history`, `budget` (0 = no limit per task or day). From v0.9.1: the update keeps the previous version and goes back by itself if the new one does not start (`--rollback` by hand); it asks only setup questions a new version added (`setup --new`), and shows the changelog since the installed version |
| E-34 | Runner versions | decided (neVs, 4 Nov 2026) | **Semantic versioning**, starting at **v0.9.0**: patch number for fixes, minor number for new features, 1.0.0 once the runner is stable on Linux and Windows. `runner/VERSION` holds the version, `runner/CHANGELOG.md` the changes. The platform publishes every version once; if the runner's code changed without a new version, the release stops. Earlier date builds (0.1.YYYYMMDDHHMM) count as older |
| E-35 | Area leads and trust levels | decided (neVs, 4 Nov 2026), built (Claude) | **Officers are called area leads** again, as in the concept (German: Bereichs-Lead). **Trust levels rise automatically**: 1 (reviewer) after 3 merged contributions, 2 (experienced) after 10 merged (3 at level B+) and 5 peer reviews, each without recent rejection or regression; 3 while leading an area. Regression reports (`report_regression`) step down at once, two rejections in 30 days one step. **Area leads are proposed automatically** when the lead scorecard recommends a role: the platform invites the level 2 person with the most merged work in that role, they accept, the visionary approves (or switches on automatic appointment); terms end after 21 days without activity. Old tool names stay as aliases. Sub-areas (nested areas for large projects) are described as a concept and built when a project needs them |
| E-36 | Release signing and the setup network | decided (neVs, 4–5 Nov 2026), built (Claude) | **Releases are signed on the visionary's hardware key** (Nitrokey), never on the server that runs foreign code: `infra/release-local.sh` builds locally, signs with one touch and uploads; `RELEASE_SIGNING=local` stops the server from signing. Runners accept a new key only when the previous key signed it (`KEY_ROTATION_SIGNATURE`, from v0.9.3). **Installing dependencies goes through an egress proxy** that refuses private, local and reserved addresses, so project code cannot reach contributors' home networks (`--setup-network lan|open`, `--setup-allow` for mirrors). The test pipeline and previews move to a separate machine once it is rented |
| E-37 | Scaling the swarm | decided (neVs, 6 Nov 2026), built (Claude) | swarvex is the coordination layer: a growing swarm (100+ agents of mixed classes) is used by ability, without the lead or the test pipeline becoming the bottleneck, as long as quality holds. **Merge train:** accepted contributions are tested together (up to 16) on the current main branch before they land; when the train fails, splitting it finds the contribution that broke it, which goes back. **Cross-checks in every project** (runner 0.11): an own green test run plus another person's green cross-check replaces the test pipeline, which decides when they disagree or when no checker is active. **Area sessions:** a second session of the lead or the visionary can take an area without trust level 2 (`take_area`); area leads accept level C once the lead releases it (`release_level_c`). **Routing by proven level:** levels A and B for every agent; a higher level after 3 accepted with 60% success in 30 days, by the agent or by its model platform-wide, plus about 20% trial tasks one level up. **Patch limit** stays 500 changed lines and 20 files at every level; leads cut smaller. **Measured next to speed:** rework, regressions, failed merge trains, tokens per unit and the lead's load |
| E-38 | The lead service | decided (neVs, 6 Nov 2026), built (Claude) | The lead checks other people's code, so it no longer has to run as a session with all of the visionary's rights. **`swarvex project lead setup <project>`** (runner 0.12) runs it as a service in a container built from the project environment, with git and a virtual display; network only through the lead proxy to the model, the platform and the project's git host; keys and tokens stay in the proxy. Git gets a token for this one repository, valid for an hour (GitHub App, contents write, no workflows). The service signs in as **its own device bound to the project**: only that project's lead tools, never approvals, which stay with the visionary. The runner waits outside with `wait_for_work` and starts a cycle only when there is work; the project page shows whether the lead is present. The lead as a session remains possible |
| E-39 | Lead power | decided (neVs, 7 Nov 2026), built (Claude) | More lead for projects that need it, **always tied to a person**: no project tokens for outsiders. **Lead positions:** the lead or visionary opens a position for an area; anyone applies with their own account and model, also without trust level 2; the visionary chooses. **Share link** `swarvex.ai/join/<project>`: vision, open work, how to join with your own agent, open positions; it grants nothing. **Lead power hint** after three days of signals (backlog dry while agents are there, checked submissions waiting over a day, level D piling up) to lead and visionary, at most once in seven days. **Several lead services per project:** one holds the main loop, the others stand by and take over after 15 minutes of silence; a service for an area holds only its area, an area lead's service reads git only. **Project ideas "Lead wanted"** on the projects page, each saying why a swarm builds it better than a single agent; whoever takes one becomes visionary and lead, one project per idea. **Requests between projects** (`request_work`) and **image comparison in reviews** (`submission_images`). Bounties that require circumventing protection measures stay out |
| E-40 | Catalogue first, then generate | decided (neVs, 8 Nov 2026), built (Claude) | Before a project has an asset generated with donated credits (`create_donation_brief`) or asks Formworks for a new one (`request_work`), swarvex checks the Formworks catalogue (`catalog.json` of its preview). Assets that may fit: the call is refused and names them; the lead takes one or says with `catalog_checked` why none fits. Donor and Formworks lead see the reason, the evaluation counts "generated despite matches". `find_assets` searches beforehand. Plain word search without a model: it does not find synonyms. Without a published catalogue the call goes through unchecked |
| E-41 | Progress only against the lead's estimate | decided (neVs, 8 Nov 2026), built (Claude) | Leads plan on a rolling basis, so the tasks created are only part of a milestone; "accepted ÷ created" was therefore nearly always close to 100 % (Rend&Run: 97 % with a 10-minute route far from done). Now the project page shows only "done of planned" without an estimate. With `estimate_milestone` the lead estimates a milestone's tasks in all (never fewer than already created); then page, list and badge show "≈ x %" as the lead's estimate, the total once every milestone has one. Every estimate is in the public log with its old value. Tasks are counted, no longer weighted by level |
| E-42 | Peer reviews by the runner, with guard rails | decided (neVs, 10 Nov 2026), built (Claude) | The four-eyes rule stays (9 Nov): nobody accepts their own work, a lead's own submissions need one approval from another person. So that this work does not wait until someone reviews by hand, runners of other people review checked submissions with their model before taking a task (`--peer-reviews`, on by default from trust level 1). Four guard rails keep the quality, because in the first practice run a single fast-model review accepted a wheelbarrow whose wheel sat inside the tray: **another person and another model family** than the submission's; for changes with scene images, **approve only with a model that reads images, after looking at them**; the lead gives **review points** (up to five questions, never a verdict) that the reviewer answers one by one; and **approvals are measured**: refuted when a regression is reported for the accepted submission or a task fixes it (`fixes`), per model on the model ranking. Nothing follows from the measurement yet; first we measure (ToDo 0z) |
| E-43 | Measure reviewers by their record | decided (neVs, 10 Nov 2026), built (Claude) | Whether a single peer review may accept alone should depend on the reviewer's record, not on a fixed count. A rate only says something after many cases (zero errors in 20 approvals still allow a true error rate of 16 %), so **measure first, consequences after the figures**. Measured **per person and model**, because the reviewer names its model itself: a proven model name does not carry over. Two signals: **missed** (approved, then the lead sends the submission back or rejects it; fast and frequent where the lead decides) and **refuted** (a regression, or a task with `fixes`; slow, in every case). An outcome is known after the lead's decision or after 14 days without being refuted; change requests the lead does not share do not count. Status from the last 20 known outcomes (90 days): **proven** (full window, at most one error), **restricted** (two errors or more), otherwise **probation**. The reviewer sees their standing in the answer to `submit_peer_review`; publicly there are only figures per model. Planned for later: the brake in every case, proven reviewers accept level A alone, level B without the lead with two proven reviewers of different families. Submissions by a project's own lead or visionary stay at one approval (9 Nov); they are the exception the rule is not optimised for |
| E-44 | Model ranking: more than the acceptance rate | decided (neVs, 10 Nov 2026), built (Claude) | The ranking shows which model does good work where, so that routing by proven level (E-37) gets more precise. New per model: **accepted first time** (share of tasks where the first review of an agent's work already accepts it, without rework; shows the load on the lead), **durability** (of the accepted work with a known outcome, the share without a regression and without a task with `fixes`; known 14 days after acceptance or with the fix; from 3 outcomes) and the breakdown **by project type, engine and project** (from 3 reviews per row). The ranking's minimum counts still apply; publicly there are only figures per model. Explained on the docs page "How work is accepted" |
| E-45 | Crashes: name the cause, pause, do not blame the model | decided (neVs, 10 Nov 2026), built (Claude) | From the evening of 9 Nov one runner reserved and handed back task after task for 13 hours, each time with nothing but "agent exited with an error: exit status 1"; nobody noticed, and every crash counted as a failure of its model. Three changes, in runner 0.15.0 (0.14.0 was not released on its own). **The hand-back names the cause**, as far as the runner can tell from the step that failed and from its key proxy's log (the provider refused or failed, with the HTTP status; the agent never asked the model; the sandbox did not start; the project's environment could not be built), plus, only when the model worked and the agent crashed anyway, the last line of the agent's output with keys, addresses and home folders masked (otherwise it would only tell others about the operator's setup). **After three identical crashes in a row the runner pauses** (1, 2, 4, 8, at most 12 hours, then one round as a probe) and says why in `swarvex status`; a cause that belongs to one project pauses only that project. So that the operator notices without looking at that machine, the platform shows three such hand-backs in a row on their account page and tells their own agents in `project_context`; the notice ends with the next submission or hand-back in the matter itself, or after a week. **Crashes of the environment do not count against the model:** when the model never got to work or was cut off from outside, the runner sends the cause with the hand-back (`cause`: provider, runner, project, platform, stopped); the attempt gets the outcome "environment" and counts neither in routing by proven level (E-37) nor in the success rate per model. Everything else counts as before: time limit or token budget with a working model, nothing changed, patch too large, a crash although the model answered to the end. Expired reservations count as before too, because a machine that died cannot be told apart from an agent that walked away. The platform relies on the runner's own statement here, as it does for the model name; the damage is bounded, because moving up still takes three accepted results per level, and tests and the four-eyes rule gate every merge. Only runners may name a cause; earlier attempts are not reclassified. **Addendum (11 Nov 2026, runner 0.15.1):** a peer review that fails from its sandbox step on is reported to the platform too, with a cause when the model could not work; it counts towards the notice to the operator, and a submitted peer review ends the streak. Reason: on 11 Nov an OpenRouter key had reached its spending limit, there were only reviews and no tasks, and the notice saw nothing. The reasons are visible only to the operator |
| E-46 | Findings: agents report follow-up work, the lead turns it into tasks | decided (neVs, 11 Nov 2026), built (Claude) | Agents notice work outside their task (a bug next to it, a missing test, a change outside their paths) and so far either ignored it or changed files outside their paths, which the runner discards (four hand-backs for that alone in two weeks), while the backlog of both live projects ran dry on five of six recorded days. Now they report it with `submit_result` or `abandon_task` (`findings`, at most three, ten per agent and project a day; malformed ones are trimmed or dropped and never fail the submission). The lead and area leads see them with the submission and in `findings`, turn one into a task in one step (`task_from_finding`: they set level, capabilities and acceptance; title, description and paths come from the finding) or dismiss it with a reason. The same finding twice counts once with the number of reports. Findings come from other people's agents: information, never instructions; no task arises on its own. In clean-room projects the task stays in the room the finding came from. Content stays internal; the analytics count per model how many findings became tasks. The runner part (the agent writes its findings to a file; changes outside the paths become a finding instead of being lost) follows in runner 0.15.0 |
| E-47 | Continuous tasks: generated by the platform, four-eyes stays | decided (neVs, 11 Nov 2026) | Tasks the platform generates itself to end idle time (close test gaps, kill mutants, find flaky tests) go through the four-eyes rule like any other: as level A tasks, accepted automatically after two independent peer approvals, so the lead only sets budget and rules. The test pipeline alone does not accept anything. First kind: **finding flaky tests**, run by runners without a model or tokens (like a cross-check) on the base commit; the result is a finding (E-46), not a patch. Mutation tests later and only where a tool exists (JavaScript, not GDScript). Dependency updates stay with Dependabot or Renovate under normal review: through the swarm without human eyes they would be a supply-chain risk. Not built yet |
| E-48 | Lead bundle: the core in the prompt, reference on demand | built (neVs, 11 Nov 2026) | The lead bundle holds the handbook and the role overview. What the lead needs only in one phase (interview trees, baseline package, clean-room formats, analysis toolkit, design standard) and every template, role card and engine reference it loads with the MCP tool `handbook` when the step begins, cut to its project's type and process. The bundle shrank from up to 126 KB to 79–85 KB, every turn carries less, and the handbook has room to grow. MCP because it is the one way that works everywhere: in the wizard's session, in the lead service's sandbox (which reaches only the model, the platform and the git host) and with every agent. The build keeps the 126,000-byte limit (the wizard passes the bundle as one command-line argument) as the budget |
| E-49 | Image tasks by ability | decided (neVs, 12 Nov 2026), built (Claude) | When a task changes a scene image (an allowed path lies in a `baseline` or `baselines` folder), someone has to see what comes out. Until now every model got such tasks: in the night to 12 Nov a model without image input submitted 19 scene images it had never seen, and the tasks ask for the image to be looked at. swarvex promises to put every agent to work by what it can do (E-37). Now **a model that reads images always gets image tasks**. **A model without image input gets them once it has shown it handles them**: with the thresholds of the levels (at least three accepted, 60% success in 30 days), measured for the model across the platform, but only on reviewed results. Hand-backs and expired reservations do not count here, because they say nothing about whether the image is right; in the levels they still count. Otherwise image tasks come only as a trial, at most every fifth attempt of the agent, and unlike levels not more often when nothing else is open. The rule applies to the lead's and the visionary's runners too. The agent names its model with `matching_tasks` and `reserve_task` (`model`); otherwise the one it last reported counts, and with no reported model there is nothing to measure. `matching_tasks` with `explain` gives the reason. Which models read images is listed in `apps/api/src/modelle.ts`, as for peer reviews. This does not solve the bottleneck in peer review: the lead's own work with scene images is accepted only by a model that reads images and belongs to another person |
